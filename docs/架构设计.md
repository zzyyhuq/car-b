# 系统架构设计

> 依据《功能结构图》（7 模块 / 25 个功能点）细化。本科毕设体量，单应用、单体部署，不上微服务、不上 RBAC 五表。

## 一、总体架构

```
┌─────────────────────┐        ┌─────────────────────┐
│  微信小程序（车主）  │        │  Web 管理端（Vue3）  │
│  原生 WXML/WXSS/JS  │        │  管理员 + 门店员工   │
└──────────┬──────────┘        └──────────┬──────────┘
           │  HTTPS / JSON (REST)          │
           └───────────────┬───────────────┘
                           ▼
        ┌──────────────────────────────────────┐
        │        Spring Boot 3 单应用           │
        │  Controller → Service → Mapper        │
        │  横切：JWT 鉴权 / 全局异常 / 统一响应  │
        └───────────────┬──────────────────────┘
                        ▼
        ┌───────────────┴───────────────┐
        │  MySQL 8 业务数据   Redis 登录态 │
        └───────────────────────────────┘
                        │
                        ▼
              微信接口（code2session 登录）
              本地文件存储（图片，毕设够用）
```

**为什么只有一个后端**：小程序和管理后台共用同一套接口，靠 JWT 里的 `role` 区分权限。这样接口只写一遍，论文里也好画图。

## 二、功能细分

### 模块 1 · 用户管理

| 功能点 | 车主端（小程序） | 管理端（Vue） | 接口 |
|---|---|---|---|
| 用户注册 | 微信首次登录自动建档 | 管理员新增员工/管理员账号 | `POST /api/auth/wx-login` `POST /api/user` |
| 用户登录 | `wx.login` 换 openid → JWT | 账号密码 → JWT | `POST /api/auth/login` |
| 用户信息修改 | 改昵称/头像/手机号 | 改任意用户 | `GET/PUT /api/user/profile` `PUT /api/user/{id}` |
| 角色权限管理 | — | 分配 ADMIN/STAFF/OWNER、启用禁用 | `PUT /api/user/{id}/role` `PUT /api/user/{id}/status` |
| **车辆管理**（补充） | 增删改查我的车 | 查看车主车辆 | `GET/POST/PUT/DELETE /api/car` |

> 车辆管理不在原图里，但订单必须关联车辆，否则"预约"落不了地。写论文时归入用户管理模块的子功能即可。

### 模块 2 · 美容订单类型管理（服务项目）

| 功能点 | 管理端 | 车主端 | 接口 |
|---|---|---|---|
| 类型新增 | 填名称/分类/图片/描述 | — | `POST /api/service-type` |
| 类型修改 | 同上 | — | `PUT /api/service-type/{id}` |
| 类型删除 | 逻辑删除（订单已引用的不能物理删） | — | `DELETE /api/service-type/{id}` |
| 类型查询 | 分页 + 名称/状态筛选 | 只看上架的 | `GET /api/service-type/page` `GET /api/service-type/list` |
| 价格配置 | 价格、预计时长、积分倍率、上下架 | 展示 | `PUT /api/service-type/{id}/status` |

### 模块 3 · 服务过程管理

| 功能点 | 员工端 | 管理端 | 车主端 | 接口 |
|---|---|---|---|---|
| 服务备案登记 | 接单后登记车辆状况、预检照片 | 查看 | — | `POST /api/process/register` |
| 服务进度更新 | 按节点推进 + 上传照片 + 备注 | 查看 | 时间线展示 | `POST /api/process/{orderId}/node` |
| 服务进程监控 | — | 看板：所有进行中订单及其当前节点 | 看自己订单 | `GET /api/process/monitor` |
| 美容记录查询 | 查自己的历史服务 | 按车牌/时间/员工/项目查 | 查自己历史 | `GET /api/process/page` |

**服务节点**（固定 5 步，存 `service_process.node`）：
`已接车 → 清洗中 → 美容施工中 → 质检 → 待取车 → 已完成`

> 节点用枚举常量写死，别做成可配置的——配置化会多出两张表，答辩时讲不明白，收益为零。

### 模块 4 · 美容订单管理

| 功能点 | 车主端 | 员工/管理端 | 接口 |
|---|---|---|---|
| 业务登记 | — | 到店客户直接开单（选车主/车辆/项目） | `POST /api/order/admin-create` |
| 预约管理 | 选服务+车辆+时间段下单；取消 | 改约、派单给员工、取消 | `POST /api/order` `PUT /api/order/{id}/assign` `PUT /api/order/{id}/cancel` |
| 订单查询 | 我的订单（按状态 tab） | 多条件分页（订单号/车牌/状态/时间） | `GET /api/order/my` `GET /api/order/page` |
| 订单状态跟踪 | 详情页看状态+进度 | 状态流转按钮 | `PUT /api/order/{id}/status` |

**订单状态机**（只在 Service 层流转，Controller 不许直接改）：

```
待接单 ──接单──> 已接单 ──开始服务──> 服务中 ──完成──> 已完成 ──评价──> 已评价
   │                  │                    │
   └──────取消────────┴────────────────────┘
              已取消（仅待接单/已接单可取消）
```

订单完成时自动触发：加积分 + 写积分流水（模块 5 依赖这一环）。

### 模块 5 · 积分管理

| 功能点 | 车主端 | 管理端 | 接口 |
|---|---|---|---|
| 积分商品管理 | 浏览商城 | 商品 CRUD、库存、上下架 | `GET /api/points/goods/page` `POST/PUT/DELETE /api/points/goods` |
| 积分兑换 | 兑换（扣分/减库存/生成兑换单） | 核销兑换单 | `POST /api/points/exchange` `PUT /api/points/exchange/{id}/verify` |
| 兑换明细查询 | 我的兑换记录 | 全部兑换单 | `GET /api/points/exchange/my` `GET /api/points/exchange/page` |
| 积分记录查询 | 我的积分流水 | 按用户查流水、手动调分 | `GET /api/points/record/my` `POST /api/points/adjust` |

**积分规则**：订单完成 `实付金额 × 服务项目积分倍率`，向下取整；兑换扣分同事务写流水。
`points_record.type`：`ORDER_GAIN` / `EXCHANGE_COST` / `ADMIN_ADJUST`。

### 模块 6 · 留言簿管理

| 功能点 | 车主端 | 管理端 | 接口 |
|---|---|---|---|
| 服务评价 | 订单完成后评价（星级+内容） | 查看 | `POST /api/message/evaluate` |
| 留言提交 | 提交意见反馈 | 查看 | `POST /api/message` |
| 留言回复 | 看回复 | 回复留言 | `PUT /api/message/{id}/reply` |
| 留言审核 | — | 通过/隐藏 | `PUT /api/message/{id}/audit` |

> 评价和留言共用 `message` 表，用 `type`（EVALUATION / FEEDBACK）区分，`order_id` 仅评价有值。少一张表，论文里一句话解释清楚。

### 模块 7 · 通知公告及活动管理

| 功能点 | 管理端 | 车主端 | 接口 |
|---|---|---|---|
| 公告发布 | 新建并发布 | 首页/列表可见 | `POST /api/notice` `PUT /api/notice/{id}/publish` |
| 公告管理 | 编辑/删除/下线 | — | `PUT/DELETE /api/notice/{id}` |
| 活动发布 | 新建（封面/起止时间） | 首页轮播、活动列表 | `POST /api/activity` |
| 活动管理 | 编辑/删除、查看报名名单 | — | `GET /api/activity/{id}/signups` |
| 活动报名 | — | 一键报名 / 取消报名 | `POST /api/activity/{id}/signup` |

## 三、角色权限矩阵

| 模块 | 管理员 | 门店员工 | 车主 |
|---|---|---|---|
| 用户管理 | 全部 | 只看自己资料 | 只看改自己 |
| 服务项目 | 增删改查 | 只读 | 只读（上架的） |
| 订单管理 | 全部 + 派单 | 接单、改状态（自己订单） | 下单、取消、查看自己的 |
| 服务过程 | 监控全部 | 登记、更新进度 | 查看自己订单 |
| 积分管理 | 商品/兑换/流水全部 | 核销兑换单 | 兑换、查看自己 |
| 留言簿 | 审核、回复 | 无 | 提交、评价、看回复 |
| 公告活动 | 全部 | 只读 | 只读 + 报名 |

**实现方式**：JWT 里带 `userId` + `role`，拦截器解析后放入 `UserContext`（ThreadLocal）；接口上用自定义注解 `@RequireRole({ADMIN, STAFF})` 校验。够用，不要引 Spring Security 的完整 RBAC。

> 注意：原技术栈写了 Spring Security，用它做认证（登录、密码加密、JWT 过滤器）没问题，但别硬套它的 `@PreAuthorize` 权限模型，学习成本高且答辩容易被追问。

## 四、后端工程结构

```
backend/src/main/java/com/example/beauty/
├── BeautyApplication.java
├── common/
│   ├── Result.java / PageResult.java         统一响应
│   ├── exception/                             BusinessException + 全局处理器
│   ├── config/                                MyBatis-Plus、WebMvc、Redis
│   ├── security/                              JwtUtil、JwtInterceptor、UserContext
│   └── util/                                  文件上传等
└── module/
    ├── auth/         登录（微信 + 账密）
    ├── user/         用户 + 车辆
    ├── servicetype/  服务项目
    ├── order/        订单 + 服务过程
    ├── points/       积分商品/兑换/流水
    ├── message/      留言 + 评价
    └── notice/       公告 + 活动 + 报名
```

每个 module 内固定分层：`controller / service / service/impl / mapper / entity / dto / vo`。
**模块之间只通过 Service 接口调用**，不跨模块直接操作对方的 Mapper——这是论文里"高内聚低耦合"那句话的实证。

## 六、管理端页面

登录 / 数据概览 / 用户管理 / 员工管理 / 服务项目管理 / 订单管理（列表+详情+派单）/ 服务进度监控 / 积分商品 / 兑换核销 / 积分流水 / 留言管理 / 公告管理 / 活动管理（含报名名单）。

## 七、开发顺序（有依赖，不能乱）

| 顺序 | 内容 | 依赖原因 |
|---|---|---|
| 1 | 基础设施：统一响应、异常、JWT、MyBatis-Plus 配置 | 所有模块的地基 |
| 2 | 用户模块 + 登录（车主微信登录 + 管理端账密） | 没有身份，什么都测不了 |
| 3 | 服务项目模块 | 没有服务项目，下单页是空的 |
| 4 | **订单模块**：下单 → 查询 → 接单 → 改状态 | 核心业务线，打通它等于打通全项目 |
| 5 | 服务过程模块 | 依赖订单存在 |
| 6 | 积分模块 | 依赖"订单完成加分"这个触发点 |
| 7 | 留言/评价模块 | 依赖订单（评价） |
| 8 | 公告活动模块 | 独立，无依赖，可以最后做 |
| 9 | Vue 管理端逐页对接 | 接口都有了，前端就是套模板 |

## 八、优先级（时间不够时可以砍的）

**必做**（少了答辩讲不完整）：用户登录、服务项目、订单全流程、服务进度、积分兑换。
**可砍**：数据概览看板、Excel 导出、订单超时自动取消（定时任务）、图片压缩、留言敏感词过滤。
**明确不做**：微信支付（要商户资质）、短信验证码（要钱）、消息模板订阅（要认证）。

> 砍功能不丢人，砍完要能说清"为什么不做"——写进论文的"不足与展望"正好。
